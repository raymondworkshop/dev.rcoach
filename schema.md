# rbrain Schema

This file defines the structural conventions for the rbrain llm-wiki pipeline.
It documents how `raw`, `atoms`, `wiki`, and related files should be organized,
what metadata each atom should carry, and how links and categories should be used.

## Purpose

- Make the second brain schema explicit and shareable.
- Let tools (`atomizer.py`, `backlinker.py`, `coach.py`, `rbrain_lint.py`) use a stable format.
- Keep `raw` content immutable while letting `atoms` and `wiki` be structured and queryable.
- Support the four high-level dimensions:
  - `self`
  - `career`
  - `relations`
  - `service`

## Repository layout

- `rbrain-wiki/raw/`
  - Immutable source notes: diaries, thoughts, learning material, fragments.
  - `raw/queries/` is reserved for coach session history and should be skipped by ingestion.

- `rbrain-wiki/atoms/`
  - Generated atom Markdown files, one entry per extracted concept, event, emotion, or pattern.

- `rbrain-wiki/wiki/`
  - Curated pages for long-form synthesis, summaries, entity and concept collections.

- `rbrain-wiki/vector_index.json`
  - Embeddings and search index used by `coach.py`.

- `rbrain-wiki/outputs/`
  - Generated reports, slides, exports.

## Atom conventions

Each atom file should follow a consistent structure.

### Filename

- Use a descriptive slug or short title.
- Prefer lowercase, hyphen-separated words.
- Avoid spaces and special characters.

Example:

- `work-bottleneck-in-q1.md`
- `trust-pattern-with-family.md`
- `service-mission-clarity.md`

### Frontmatter

```yaml
---
title: "..."
date: "YYYY-MM-DD"
source: "raw/<filename>.md"
category: "self|career|relations|service"
tags:
  - "#emotion"
  - "#decision"
  - "#learning"
  - "#habit"
summary: "One-sentence essence of this atom."
---
```

Recommended fields:
- `title`: short human-readable label.
- `date`: the date of the source note or event.
- `source`: origin path relative to `rbrain-wiki/raw/`.
- `category`: one of the four main dimensions.
- `tags`: more granular labels for later retrieval.
- `summary`: concise description of the atom.
- `perspective` (optional): `self`, `other`, `society`.
- `classification` (optional): list like `decision`, `problem`, `learning`, `observation`.
- `emotion_triggers` (optional): list of moods or emotional words found in the text.
- `status` (optional): `draft`, `verified`, `archived`.

### Body structure

Example:

```markdown
## Overview
A short explanation of what this atom captures.

## Evidence
> "Verbatim sentence from raw note."

## Insights
- Observation 1
- Pattern 2

## Links
- [[related-atom]]
- [[personal-growth]]

## 🔗 Backlinks
(This section is generated by `backlinker.py`.)
```

### Recommended categories and tags

Core categories:
- `self`
- `career`
- `relations`
- `service`

Suggested tags:
- `#emotion`
- `#stress`
- `#motivation`
- `#decision`
- `#learning`
- `#habit`
- `#challenge`
- `#opportunity`
- `#mission`
- `#value`
- `#pattern`
- `#question`

## Wiki page conventions

Wiki pages are curated, long-form, and often reference multiple atoms.

### Types of wiki pages

- `entities/`: people, organizations, places, projects, systems.
- `concepts/`: recurring ideas, emotional patterns, frameworks.
- `summaries/`: reflections, chapter summaries, topic overviews.
- `growth-trajectory.md`: long-term synthesis of patterns, evolution, and future orientation.
- `personal-growth.md`: self-awareness, habits, mindset.
- `career-business.md`: work strategy, execution, learning.
- `relations-social.md`: relationship patterns, communication, boundaries.
- `service-society.md`: social impact, contribution, mission.

### Wiki page structure

Each wiki page should include:
- a short introduction
- evidence or citations to atoms / raw notes
- explicit observations or patterns
- actionable conclusions or next steps
- `[[wikilinks]]` to atoms and other wiki pages

## Link conventions

- Use `[[double bracket links]]` for internal graph linking.
- Use consistent atom titles and wiki page titles.
- If a link target changes name, update both source and destination.

## Validation and linting

Tools should validate:
- required atom frontmatter fields exist
- `source` references real `raw/` files
- `category` is one of the allowed four options
- tags follow the chosen domain/tag conventions
- `## 🔗 Backlinks` exist in atoms after backlinking

## Optional automation

`rbrain-schema.py` can be added later to encode this schema programmatically.
It can also become the validator for generated atoms and wiki pages,
so the pipeline can reject inconsistent or malformed entries.

## Notes

- The schema is a guide, not a rigid rulebook. Use it to keep the system coherent.
- The strongest value comes from linking evidence to insight and then to action.
- Keep `raw` immutable; let `atoms` and `wiki` evolve.
